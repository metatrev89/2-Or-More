# 2+ — Project Brief for Claude sessions

2+ is a mobile app (React Native/Expo, iOS + Android) for AI-driven affirmations:
conversational goal intake → present-tense "I am" statements → daily delivery as
text, audio in the user's own recorded voice (or a preset AI voice — no cloning in v1),
photo-real goal images, and a stitched "mind movie."
Named for "wherever two or more are in agreement." Owner: Trevor Spencer.

## Key implementation facts
- Life areas (DECIDED Sept 5, 2026 — supersedes the original 7): chakra-mapped, root→crown, per Trevor's Meta AI reference convo (`backend/reference/meta-intake-reference.json`): health_body (Root·Foundation), emotions_creativity (Sacral·Flow), career_purpose (Solar Plexus·Drive), relationships_love (Heart·Connection), communication_expression (Throat·Voice), mindset_growth (Third Eye·Clarity), spirit_purpose (Crown·Unity). Backend `LIFE_AREAS`/`AREA_META` (types.ts) and app `AREAS`/`AREA_CHAKRAS` (theme.ts) MUST stay in the same order — areaIndex crosses the API as a number. DB migration 0003. "I AM" statement style (REWRITE_SYSTEM): 2-4 sentences, "I AM" capitalized, user's specifics kept, the WHY woven in ("I have this because…"), ends on purpose not goal.
- Catch-all + NO boilerplate affirmations (DECIDED Sept 9, 2026): after the seven areas the interviewer asks ONCE whether anything else belongs in the practice (`LifeArea 'open_capture'`, backend areaIndex 7, DB migration 0004). A real answer becomes the optional 8th goal/affirmation; a decline ("no", "No, that's it", "I'm good, thanks" — `isDecline()` in `services/intake.ts`, words-only match so a refusal never becomes an affirmation) ends the intake at seven. `open_capture` is NOT a chakra: it stays out of `LIFE_AREAS`/`AREAS`, never lights a progress segment, and earns no star or chime — which is what keeps the 7-segment bar and the areaIndex contract intact. `AffirmationService.identityStatements()` was DELETED: two hardcoded lines ("I am positive…", "I stay in God's presence…") used to be appended to every set and surfaced as a generic #8 and #9 the user never said. Every affirmation must trace back to something the user actually told us — never staple set-level boilerplate onto the end again.
- Voice recording flow (BUILT Sept 11, 2026): because v1 has no cloning, **playback IS the recording** — so there is ONE take per affirmation, keyed by affirmation id (never index — indexes shift). `app/src/audio/voiceRecordings.ts` (mic permission, audio-session mode, move take out of cache into `documentDirectory/voice/`), `app/src/screens/VoiceRecorderScreen.tsx` (card-by-card guided recorder; route param `affirmationId` = re-record one, no param = walk the set from the first un-recorded). Entry points: creation moment's "My own voice", plus Home (per-affirmation "Record in my voice" on an expanded card, and a record-all prompt that disappears at full coverage). **Nothing is gated behind recording** — every card is skippable and un-recorded affirmations play in the preset AI voice (Trevor, Sept 11). Storage: Supabase Storage bucket `voice-recordings`, private, per-user RLS via `<auth.uid()>/` path prefix (migration 0005); upload is best-effort background sync in `app/src/api/voiceUpload.ts` — the local file is the source of truth for playback and a failed upload must never undo a save. R2 stays deferred with the media layer.
- Persistence (BUILT Sept 12, 2026 — closes the biggest v1 gap): until now NOTHING was ever written to the database. Affirmations lived only in the stateless session blob round-tripping through the phone and in the in-memory store, so they vanished on relaunch and Home fell back to `MOCK_AFFS`. Trevor lost a full real set this way, leaving 7 voice recordings keyed to affirmation ids that existed nowhere. `app/src/api/affirmationsRepo.ts` now saves goals + affirmations right after generation (BuildScreen) and loads them on Home mount. Writes use the USER'S OWN JWT — RLS policies (`own goals` / `own affirmations`, FOR ALL USING auth.uid() = user_id; Postgres applies USING to inserts when WITH CHECK is omitted) enforce ownership, so no service-role key goes on the Worker and the backend stays stateless. Backend ids are preserved on save because voice recordings are keyed by affirmation id.
- Audio playback (BUILT Sept 12, 2026): Home and the Player used to fake playback with `setInterval` against no audio at all. `app/src/audio/useAffirmationQueue.ts` is the real engine (expo-audio, sequential, skips un-recorded entries); `app/src/audio/affirmationAudio.ts` resolves each affirmation to a local recording → signed Supabase Storage URL → null. **v1 has exactly ONE audio source: the user's own recording.** Fish TTS is still `PROVIDER_TTS = "mock"`, so un-recorded affirmations have NO audio — the UI must say so, never play silence. Play-all supports real `setPlaybackRate` speed, loop off/once/infinite, and a 15/30/60-minute timer that loops and stops at the next track boundary (never cuts a statement mid-sentence).
- Persistent mini player (BUILT Sept 12, 2026): playback lives in ONE app-level session (`app/src/audio/AudioSession.tsx`) mounted ABOVE the navigator, which is what lets audio survive screen changes. **Never create a second `useAffirmationQueue`** — two instances each own an expo-audio player and play over each other; Home and Player both consume `useAudioSession()`. Ring bookkeeping + celebrations live in the provider so a ring closes no matter which screen is showing. `MiniPlayer.tsx` (expand ⌃ left, play/pause, title + live scrub, X right) renders from App over every screen except `Player`, `pointerEvents="box-none"` so the UI stays interactive; `SessionCeleb.tsx` fires the completion celebration over ANY screen and closes the session on dismiss. The overlays sit inside a `<View style={{flex:1}}>` within NavigationContainer — it renders children without a flex wrapper, so absolute positioning needs its own positioned parent.
- Alignment CUT from v1 (DECIDED Sept 11, 2026): the whole "how aligned did that feel?" layer is gone — the post-session `MoodCheckIn` (Disconnected / Aligned / Fully Aligned, file deleted), the store's `moods` slice + `recordMood`, `timing.moodDismissMs`, Progress's ALIGNMENT card, its `AlignMark` glyphs and `sessionMark()` classifier, and Home's terracotta 2nd ring. It was never computed from anything — every number and mark was a hardcoded design placeholder (`i === 1` meant "the 9:30 session is disconnected"), so it asserted a judgement the app could not actually make. `SessionCeleb` lost its `autoDismiss` prop with it: that flag existed only to hold the celebration open for an un-answered mood picker, so it now always times out at 4s. Don't reintroduce a subjective-quality signal without real data behind it. **Session percentages are completion-only now**, coloured by thirds via `pctColor()` in ProgressScreen: terracotta <1/3, gold <2/3, teal above. Terracotta/gold/teal IS this app's red/yellow/green — literal traffic-light red stays banned (Trevor chose the palette trio over true RGB when asked). Teal-for-completion is long-standing precedent here (every progress ring is teal) and does not loosen the "teal = AI actions" rule elsewhere.
- Social = TWO-WAY CONNECTIONS, no comments (DECIDED Sept 11, 2026): follow / follow-back is gone. `Connection.status` in `api/socialMock.ts` is `connected | incoming | outgoing` — the old shape carried `pending` AND `followsYou`, which could express "follows you but you don't follow them", a state that cannot exist now. Friends tabs are **Connections / Requests / Invites**; Requests splits Received (Accept or decline) from Sent (Pending, Cancel only) because the available action differs by who is waiting. Discover's "Add back" is now "Requests → Accept", and its suggested-people CTA resolves to **Pending**, not "Added" — asking someone leaves you waiting on them. Home's notification sheet says "wants to connect" with Accept + decline. **Feed comments are cut from this version** (composer, thread, `FeedItem.comments`, and the `comment` notification type all removed): Affirm is the only post interaction, so there is still exactly one way to respond and it is positive. Deferral rationale + what to reopen is in `UI-UX Backlog.md` §4. The tab is still labelled **Friends** — the brand doc's 5-tab nav is non-negotiable, so the model changed and the tab name did not.
- **Floating tab bar clears nothing by itself**: `GlassTabBar` is absolutely positioned and painted by the navigator, so it draws OVER anything a screen renders, including modals and sheets. Any screen-level overlay must stop above it — Home's notification sheet sits at `(insets.bottom || 12) + 74`. A full-screen scrim will NOT cover the bar; if an overlay must truly own the screen, render it from `App.tsx` above the navigator like `MiniPlayer`/`SessionCeleb` do.
- Intake chat laid out to Meta's proportions (DECIDED Sept 11, 2026, from Trevor's screen recording): three goals, all about reading width. (1) **Header compacted ~155pt → ~90pt** — the centred `Wordmark` row is gone (Intake is reached from three branded screens in a row, so it repeated what the user just saw), and the segment bar now shares a hairline row with the skip link. (2) **AI replies are full-bleed text, not bubbles** — the old white bubble was capped at `maxWidth: '78%'` AND indented past the spark, throwing away roughly a third of every line. The `AiSpark` + "2+" label moved ABOVE the text on its own row (keeps the brand's "show the work" rule) and prints only on the FIRST message of a consecutive AI run, so a multi-message answer reads as one voice. Body type 15.5/22 → 16.5/25. User messages stay bubbles — the asymmetry is the point, it's what makes the transcript scannable. (3) **Submit dismisses the keyboard and pins the sent message to the top** (`pinSent()`), so the whole screen below belongs to the answer. This needs THREE measurements — `msgY` per message, `listH` on an inner wrapper, `viewportH` on the ScrollView — plus a `tailSpacer` runway, because `scrollTo` clamps at the content end and without spare height the message stops partway up. The spacer is sized to the shortfall only (`viewportH - (listH - pinY) - 28`) so it collapses to zero once a reply fills the screen. **Do not re-add `scrollDown()` after a reply lands** — that shoves the pinned question back off the top and undoes the whole thing; `scrollDown` is now only for the opening welcome and photo attach. Composer is `multiline` with `submitBehavior="blurAndSubmit"`, which is what makes Return send and drop the keyboard in one gesture.
- Scheduling (DECIDED Sept 14, 2026): **Prime protocol ladder is 5× → 4× → 3× in perpetuity** (was 10 → 5 → 3; the 10× opener was nearly an interruption an hour). `PRIME_OPENING_RINGS` in HomeScreen **must track the first rung** — it was a bare `10` and briefly promised ten rings for a plan that sends five. The "about N min of your day" line under the ladder is derived from the opener too (now 3 min). **Active window is editable on BOTH plans; quiet hours is shown on NEITHER** — it was never independent, the window steppers derive it as the exact complement (`qEnd = awStart`, `qStart = awEnd`), so the row restated in reverse what the user had just set. `qStart`/`qEnd` stay in the store and stay accurate because notification scheduling reads them; ProgressScreen's edit panel still shows them read-only, which is the last surviving reference.
- Intake phase is SERVICE-OWNED, never model-inferred (FIXED Sept 14, 2026): a live session double-asked the follow-up in area 1 and skipped it entirely in area 2. Two causes, both now closed. **(1) The model was guessing the step.** `advance()` wipes `session.turns` at every area boundary, so on the first message of an area the model saw nothing but a context line and had to pick one of the three message patterns itself — it drifted, non-deterministically. `IntakeService.phase()` now derives `goal | why | catch_all` from how many times the USER has answered and passes it as a `PHASE:` directive that INTAKE_SYSTEM declares to be an order, not a hint. `session.lastWhy` carries the previous area's why across the wipe so the "receive the why" opener has something real to receive. **(2) Area completion counted ASSISTANT turns.** A retried or double-fired `/intake/answer` pushes a second assistant turn with no answer between, so two questions + one answer read as a finished area — the area closed a question early AND the duplicate surfaced as a second follow-up, which is exactly the reported symptom. It counts user answers now (`ANSWERS_PER_AREA = 2`); a duplicate question is harmless. The API returns `phase` and the app echoes it back instead of keeping its own counter. Tests cover the full goal/why sequence across all seven areas plus the catch-all, the duplicate-question case, lastWhy hand-off, and skip. **The catch-all runs TWO beats too** (Trevor, Sept 14): the optional ask, then — only if they named something — a why, so `phase()` returns `catch_all` then `why`. Without it the 8th affirmation was the only one in the set written with no why, and therefore the only one that couldn't end on purpose, which is the entire REWRITE_SYSTEM house style. `isDecline()` runs ONLY on the first catch-all answer — a thin why like "no real reason" is brush-off vocabulary end to end and would otherwise delete a goal the user had already named. Skipping the catch-all's why KEEPS the goal (`skipArea` special-cases it): they asked to stop elaborating, not to withdraw the thing they just told us.
- Profile photo capture lives in ONE module (FIXED Sept 14, 2026): `app/src/media/profilePhoto.ts`. Two bugs Trevor hit, both from the same logic existing three times (ProfileScreen / CreationScreen / IntakeScreen) with different subsets of the fix. **(1) The first camera attempt silently failed, the second worked.** On iOS the permission alert is still animating away when `launchCameraAsync` presents, and presenting over a dismissing view controller fails — the promise just resolves `canceled: true`. Attempt two worked because permission was already granted so there was no alert to collide with. Fix: `get*PermissionsAsync` first, only prompt when undetermined, then wait `ALERT_SETTLE_MS` before presenting. Callers pass `settleMs` for the same reason when a sheet is closing. **(2) The photo vanished on relaunch.** CreationScreen and IntakeScreen stored the picker's CACHE uri verbatim — so the onboarding path, which is the one almost everyone takes, was always on borrowed time. ProfileScreen did copy into Documents but stored the ABSOLUTE path, and the iOS container UUID in `file:///var/mobile/Containers/Data/Application/<UUID>/Documents/…` changes on update/reinstall, so the string went stale while the file was fine. **Store the BASENAME, rebuild the directory at read time** — `photoNameFrom()` reduces legacy absolute paths to the same basename, so old installs migrate on first hydrate with no separate migration, and `photoExists()` drops entries whose file is really gone instead of leaving a broken `<Image>`. Same lesson as voice recordings: anything the user creates must be moved out of the cache and addressed by name, not by path. **Never call `ImagePicker.launch*` directly** — go through `pickProfilePhoto()`.
- **`getCurrentRoute()` returns the DEEPEST route, not the stack screen**: inside the tab navigator it reports 'Home'/'Feed'/etc., never 'Main'. `App.tsx` had `liftForTabs={route === 'Main'}`, which was therefore always false — the mini player used its no-tabs offset and sat 50pt INSIDE the glass bar (Trevor, Sept 14). Use `getRootState().routes[index].name === 'Main'` for "are the tabs showing"; the leaf name can't tell you, and 'Friends' is both a tab and a pushed stack screen so it can't disambiguate either. Overlay offsets derive from the exported `TAB_BAR_TOTAL_H` now, not hand-tuned numbers.
- **expo-audio `replace()` is async, like `seekTo()`** (FIXED Sept 14, 2026): `player.replace(src)` then `player.play()` on the next line often plays nothing, because the source isn't loaded yet — that's why play-all stalled between tracks. Worse, while the swap is in flight the status still belongs to the OUTGOING track, so a lingering `didJustFinish` fired `advance()` a second time: it closed the next track's ring and jumped past it without ever playing it ("track 2 never played, it went to track 3"). `useAffirmationQueue` keeps a `pendingSrcRef` — the optimistic `play()` stays for the already-loaded case, a `status.isLoaded`/`status.duration` effect starts it for real when the load lands, and **finish events are ignored entirely while a swap is pending**. Rate must be re-applied after every `replace()`; it resets.
- Ring ↔ affirmation ↔ chime is ONE sequence (FIXED Sept 15, 2026): Trevor reported rings not matching their affirmations and chimes that misfired or went missing. Three causes. **(1) The Sept 14 swap guard was unbounded.** `pendingSrcRef` only cleared in the load-confirmed effect, so if that never fired (status already loaded, duration unchanged) the flag stuck and EVERY later finish was swallowed — rings and chimes silently stopped. It's a time window now (`SWAP_GUARD_MS = 350`, `swapAtRef`): it cannot get stuck, and no affirmation ends inside a third of a second, so nothing genuine is discarded. **(2) Chimes fired on repeats.** `completeAffirmation` chimed whether or not a ring actually closed, so a second pass with loop on re-chimed every track while closing nothing — indistinguishable from a misfire, and it teaches the user the sound means nothing. It returns early when `wasDone`: no ring close → no chime, no star. A replayed set is silent by design. **(3) Ring fill could belong to the wrong track.** During a swap `index` has already advanced while `currentTime`/`duration` still describe the outgoing track, so screens dividing one by the other flashed the incoming ring nearly full. `trackFrac` is computed in the queue (0 while settling) and shared by PlayerScreen and MiniPlayer — **don't recompute `position / duration` in a screen.** Also fixed: "closes ring 7" was hardcoded and named the wrong ring for an 8-affirmation set.
- **Chimes: the THIRD fix, and the one that was actually wrong** (FIXED Sept 20, 2026). Sept 14 and Sept 15 both addressed STALE finishes; the real remaining bug was the opposite — MISSING ones. The finish effect had deps `[status.didJustFinish]`, so React only ran it when that boolean CHANGED. `replace()` does not reliably clear `didJustFinish`, so after track 1 the flag could sit at `true` indefinitely: no transition → no effect → no `onFinished` → **no ring and no chime for tracks 2..N**. Exactly one chime per session, on the first track, which is why "one ring one chime" looked correct in isolation. Fix: depend on the whole `status` object and detect the rising edge by hand (`sawFinishRef`), plus clear that marker in `playAt` so a new track can produce its own edge even if the flag never went false. Depending on `status` also means `advance` is always the current closure instead of one captured whenever the boolean last flipped. **Never key a player-event effect on a single status boolean** — expo-audio does not guarantee it toggles.
- **Chimes: the FOURTH fix — stop reading `didJustFinish` at all** (FIXED Sept 22, 2026). The Sept 20 rising-edge detector had a hole: it wrote `sawFinishRef.current = finished` (consuming the edge) BEFORE the `SWAP_GUARD_MS` check discarded it. A stale finish from the outgoing track — the exact event that guard exists for — therefore burned the latch, so when the incoming track genuinely ended there was no transition left to detect and that ring never closed or chimed. Whether it happened depended on whether the stale event landed inside the 350ms window, which is why the misfires looked *random* rather than systematic. **Not consuming the edge is not a fix either** — a latched `true` would then fire the moment the window expired and skip the track (the Sept 14 bug). And a simulation of my own first attempt showed the flag can stay latched for the whole of the NEXT track, which defeats any scheme requiring it to be false. **A signal unreliable in both directions cannot be made reliable by edge detection.** The engine now ignores `didJustFinish` as a trigger entirely and uses position + `playing`, which the player cannot misreport: `armedRef` latches when a track shows real progress (`isLoaded && playing && currentTime > 0.15`), and finish is `stoppedAtEnd` (`!playing` AND (`didJustFinish` OR `maxPos >= duration - 0.35`) — generous, since real audio often runs short of its reported duration) OR `playedOut` (`currentTime >= duration - 0.06` — tight, because it fires mid-playback and must not clip the last word). `maxPosRef` tracks the furthest point reached so a player that zeroes `currentTime` on ending is still recognised. Verified by simulating 8 status streams (clean, stale finish, permanently latched flag, zeroed currentTime, audio shorter than duration, no finish event at all, all of those combined, and a mid-track user pause): every track fires exactly once in all 8, and a pause that is never resumed correctly does NOT fire. `sawFinishRef`/`finishedAtRef` are gone. **`SWAP_GUARD_MS` survives but now only feeds `trackFrac`/`settled`, not the finish path.**
- Session end is ONE movement (BUILT Sept 22, 2026): last affirmation completes in the play-all Player → `SessionCeleb` owns the screen ~4s → on dismissal the Player **closes itself** and lands the user on Home → Home's two stat cards pop **together** with one chime as they update. `App.tsx`'s `endSessionCeleb` does the navigating (`navigate('Main', { screen: 'Home' })`, which required typing `Main` as `NavigatorScreenParams<TabsParamList>`); **`goBack()` is wrong here** because it returns to whichever tab was last active, so opening the Player from Progress would strand the celebration on a screen with no stat cards. No new coordination was needed — Home's stage-two effect was already gated on `bigCeleb` clearing, and the same dismissal clears it. `STAT_CELEB_ENTER_DELAY_MS = 420` matches the stack transition so the pop isn't spent while Home is still sliding in. **Both cards fire simultaneously now with ONE chime** (Trevor, Sept 22 — supersedes the Sept 20 left→right stagger; `STAT_CELEB_STAGGER_MS` is gone): two identical chimes at the same instant aren't a chord, they're one louder chime plus a doubled haptic.
- Home stat celebration (BUILT Sept 20, 2026): closing a SESSION pops the two Home stat cards left → right, `STAT_CELEB_STAGGER_MS = 560` apart, each with its own small chime (and therefore its own haptic — `playSfx` always fires one). Triggered off `track.today.ringsClosed` increasing, NOT off a screen's own state, which is what makes it work identically from the Home reader flow and from the play-all Player. Two-stage so it can't collide with the full-screen `SessionCeleb`: stage one only records that a celebration is OWED, stage two runs it once `bigCeleb` clears — so coming back from the Player it plays on arrival at Home. `prevRings` starts null and the first render only establishes a baseline, so opening the app on a day with sessions already banked never celebrates old work. Gold border flash + 5% scale is intentional restraint: these are glanced at, so the job is to pull the eye, not to perform.
- Background / lock-screen playback (WIRED Sept 15, 2026 — **native capability NOT available in Expo Go**): `app/src/audio/audioMode.ts` is the one place the playback session is configured — `shouldPlayInBackground: true`, `interruptionMode: 'doNotMix'` (REQUIRED for lock-screen controls; without exclusive focus the OS may not bind them to our player), `playsInSilentMode: true`. `useAffirmationQueue` claims the lock screen on the first track (`setActiveForLockScreen`), retitles per swap (`updateLockScreenMetadata`), and releases on stop (`clearLockScreenControls`); metadata comes from `AudioSession`'s `lockScreenMeta` — the statement IS the title, trimmed to 84 chars, with the area as album. expo-audio's single-player lock screen has **no next/previous**, only seek. **The JS is necessary but not sufficient**: `UIBackgroundModes: audio` comes from the expo-audio config plugin (`enableBackgroundPlayback`, now explicit in app.json), and config plugins only take effect when a NATIVE BINARY is built — Expo Go runs its own prebuilt Info.plist, so a dev build or TestFlight is the supported path. The Expo docs never state the Expo Go case either way, so whether it happens to work there is empirical, not guaranteed. **`exitRecordingMode()` now calls `restorePlaybackMode()`** — it used to set `{ allowsRecording: false, playsInSilentMode: false }`, which would have silently killed background playback for the rest of the session after a single recording. Never zero the audio mode out; always restore it. Side effect to remember: `playsInSilentMode: true` means celebration chimes also ignore the hardware silent switch, which is part of why the chime mute toggle exists.
- Chime mute (BUILT Sept 15, 2026): `store.chimesMuted` persisted under `twoplus_chimes_muted`, pushed into `sfx.setChimesMuted()` on every set and on `hydrate()` — sfx keeps a module-level flag because chimes fire from the audio session, screens and the intake, none of which should have to thread it through. **Muting takes the haptics with it**: the buzz exists to accompany the chime, so leaving it would still interrupt someone who asked for quiet. The toggle sits right of the sleep-timer chips in PlayerScreen and uses the ring-completion mark itself (`ChimeToggleIcon`) rather than a speaker, so the icon names what it silences; muted hollows the mark to inactive AND adds a slash, because a slash over a still-teal check reads as "ring not done".
- Session tracking is REAL (BUILT Sept 17, 2026): until now essentially none of it was. `homeReadDone` was the only live value — memory-only, keyed by INDEX, and **never reset**, so "today's rings" meant "since this launch" and never rolled over at midnight. `ringsDone` was literally `Math.min(4, …)` (always "4/5"), `streakDays` was a literal `12` nothing ever wrote, and the week bars, `92%`, today's-sessions list, medals and "JULY SO FAR" were all hardcoded. Worse: **`api.recordExperience()` POSTed to `/events/record`, a Worker route that does not exist** — every event 404'd into a bare catch, so the app had been silently discarding its own history. `experience_events` had existed since migration 0001, with correct RLS, never written to.
  - **THE MODEL** (Trevor's words): "individual affirmations as one data point, then sessions as another data set. Sessions are the user's total number of affirmations. So I can do a session and only complete say 5/8 — that would be my progress percentage for that session." So: affirmation = one experience; **session = one pass over the whole set, partial is normal**; day = `perDay` sessions from the schedule. A session is anchored to a scheduled SLOT (last slot at or before the event; anything before the first credits session 0) so "which session was that?" doesn't depend on when the app was open.
  - `app/src/tracking/sessions.ts` is the pure model (no RN imports, date-injectable), `useTracking.ts` adds the schedule, the clock and the store — it re-derives the current slot every minute, which is what makes rollover real. `api/sessionsRepo.ts` writes **direct to Supabase under the user's JWT**, not through the Worker (which is stateless and still has no auth); mock ids that aren't UUIDs send `affirmation_id: null` rather than failing the FK and losing the event. Local log persists to `twoplus_day_log` and is the source of truth for rendering; the server copy is merged in (union) on Home mount so a reinstall or second device restores the streak.
  - **`streakFrom` must walk CALENDAR days, not the log's keys.** The first version iterated `Object.keys(log)`, so a gap week [Mon, Thu, Fri] counted as a 3-day streak — days with no practice simply aren't in the log. Caught by `sessions.verify.ts`. The app package has **no test runner**; that file is standalone (`npx tsx src/tracking/sessions.verify.ts`, 26 checks) until `app/` gets one.

Slot count IS the day's session target, so tracking reads it: if it drifts, every ring count is wrong.

- **VOCABULARY (Trevor, Sept 22 — use these words in conversation):** an **affirmation** is one statement; a **session** is listening to/reading ALL your affirmations, one full pass, regardless of whether it's completed; a **track** is one of the day's scheduled slots (what the UI and earlier notes called a "session"). The code still says `SessionPass` for a session and `slot` for a track — **the screens were deliberately not renamed**, so when reading code translate: pass→session, slot→track.
- **A VISIT claims a track** (BUILT Sept 22, 2026): "whenever the user closes the app and reopens it to do a new session it will count as a new track." **The clock cannot answer "which track?" on its own** — four sessions back-to-back at 9am is ONE track repeated (×4), while 9am then closing the app and returning at 9:20 from a push is TWO tracks, and the clock reads the same slot in both. What separates them is the VISIT. `store.visitSeq` bumps on launch and on every `AppState` → `active` (the push-notification path); `store.slotClaim` pins the visit to the track its first session opened, so repeats in one sitting stack there. The claim dies on a new visit, a day rollover, or the clock crossing into another slot. `trackForNewSession()` then picks: the clock's track if untouched, else the next untouched one, else **scanning BACKWARDS** — so five evening sessions fill tracks 4,3,2,1,0 rather than stacking, claiming the NEAREST missed track (8pm is closer to the 6pm track than the 7am one) and each row still shows its real completion time. All tracks spoken for → extras pile onto the clock's track as repetitions. Neither `visitSeq` nor `slotClaim` is persisted: a cold start is a new visit by definition.
- **The Player's auto-close didn't fire — stale closure, same family as the chimes** (FIXED Sept 22, 2026). `SessionCeleb` did `setTimeout(onDone, 4000)`, which froze the FIRST `onDone` closure. That closure was built in the same commit the celebration appeared in — the commit where `advance()` had only just called `pause()`, so expo-audio's status still read `playing: true`. Four seconds later the stale closure asked "is playback still running?", got an answer from a moment long past, and declined to navigate. Fix: `onDoneRef` in SessionCeleb plus `sessionRef` in `App.tsx`, so both re-read at fire time. **A decision made at mount and acted on seconds later must re-read the world, not remember it** — that is now three separate bugs from this exact mistake.
- **PASSES, not a flat id set — the log's second shape** (BUILT Sept 22, 2026). Trevor wanted to listen on loop and have every lap count, with rings resetting the instant one closes. The old `SlotLog = Record<number, string[]>` made a second listen literally *unrepresentable*: the ids were already in the set, so the distinct count didn't move and the rings stayed full. Now `SessionPass { ids, closedAt? }` and `SlotLog = Record<number, SessionPass[]>`. The last pass in a slot is the live one; when it fills it closes and the next experience opens a fresh empty one. **The ring reset falls out of the data** — `currentDoneIds` reads the OPEN pass, so nothing has to remember to clear anything. `closedAt` (minutes-of-day, stamped at close because it can't be recovered later) is what lets Today's Sessions show a real completion time. **`withExperience` now needs `affCount`** to know how long a full pass is; it stays idempotent WITHIN a pass (scrubbing back doesn't inflate) but counts across passes. `migrateLog()` upgrades the old shape on hydrate — a legacy slot becomes one pass with no `closedAt`, so existing installs keep their streak and those rows just fall back to the scheduled label rather than inventing a time. `loadExperienceLog` **replays events through `withExperience` in timestamp order** rather than bucketing by hand, because passes are order-dependent — a second lap only exists because the first one filled. `mergeLogs` pairs passes by position, unions ids, keeps the earliest `closedAt`; best-effort, not a CRDT, biased toward keeping work.
  - **THE TWO HALVES OF THE RULE pull in opposite directions, and both are deliberate** (Trevor's words: "That session should count as 80% total for the daily total but still keep the other 4 slots for the day open"). `dayPct` = total passes ÷ scheduled sessions, so **four laps on a five-session day is 80%** — repetitions carry FULL day credit and dayPct may exceed 1.0 (callers cap it for ring geometry, never for the number). But `ringsClosed` counts SLOTS with ≥1 finished pass, so four laps at 9am is **one** slot attended and the other four stay open for their own times. Five laps back-to-back therefore reads 100% for the day while still showing four open slots. Don't "fix" one of these to match the other.
  - **The celebration nearly killed the loop.** `dismissBigCeleb` used to unconditionally `close()`, which stops the queue — so on loop or a sleep timer the big celebration would have stopped the very audio the user asked to repeat. It now closes only when `queue.playing` is false, and `App.tsx`'s `endSessionCeleb` uses the same signal before navigating out of the Player. Each lap gets its own celebration when it closes.
  - Today's Sessions rows show **`Session 1…5` until completed, then the actual completion time**; the old row always showed the slot's *scheduled* time, which read as a promise the user never made ("7:00 AM" still sitting there at 9pm). Dots show the OPEN pass and clear between laps; a completed session fills every dot so it still reads done at a glance, and `×N` in gold carries the rep count. 48 checks in `sessions.verify.ts`.
- **Streak rule was set impossibly high** (FIXED Sept 22, 2026): Trevor — "the day streak counter is not reading accurately." Not a rendering bug. The rule was `dayPct >= STREAK_THRESHOLD (0.5)`, and `dayPct` is the MEAN completion across every scheduled slot — so on the prime protocol's 5-sessions-a-day opener, finishing **one whole session scored 1/5 = 0.20 and the day did not count.** Measured: four consecutive days each with a completed session returned a streak of **0**; a day needed 2.5 complete passes over the set to register. It also contradicted the model this app is built on (partial sessions are normal) and the brand rule (encouraging, never condemning). Now `dayCountsForStreak(d) => d.dayPct > 0` — **a streak answers one question, did you show up.** Completion quality is still reported honestly elsewhere (per-session %, week bars, `ringsClosed`). The old constant survives as `PAUSE_THRESHOLD = 0.5`, used ONLY for the "streak paused" note — a quiet day is worth a gentle mention without cancelling the streak. **The four pre-existing streak tests all used fully-complete days, which is why they passed through the entire bug**; `sessions.verify.ts` now has four more built from the shapes real users produce (one full session out of five, a 1-of-4 partial, gaps between partial days), 30 checks total.
- Progress hero is the DAY, not the session (CHANGED Sept 22, 2026): it read `readCount/affCount` — "8/8" — which was the current session's affirmations, so it hit 100% as soon as one pass finished and said nothing about the other four sessions the schedule asked for. The sub-copy under it says "this session's ring" now — with the ring above being the day, the two would otherwise contradict each other at 100% of a single session.
- **Week charts read NEWEST → OLDEST — today is the LEFTMOST bar** (Trevor, Sept 22). Applies to both Home's sparkline and Progress's labelled chart, and they must stay in step. `summarizeTracking().week` is still chronological (oldest → newest) because `weekPct` and the paused-day scan depend on that order — **the flip is display-only** (`.reverse()` at render), and Progress's `weekDayLabels` counts forward from today rather than back from six days ago. Today's label is index **0** now, not `length - 1`, which is what gets the ink colour. It stays a rolling seven days, not a calendar week.
- **Centred flex containers don't clip — they spill**: PlayerScreen's quote block was `flex: 1, justifyContent: 'center'`, which looks right until the content is taller than the space, then it overflows in BOTH directions and lands on the waveform below. Real "I AM" statements are 3-4 sentences, so that was the normal case. It's a ScrollView with `contentContainerStyle={{ flexGrow: 1, justifyContent: 'center' }}` now (short statements still centre), plus the serif steps 27 → 23 → 20pt by length so most never need to scroll.
- **RN gotcha — `multiline` TextInput needs a DRIVEN height**: with `multiline` and no explicit `height`, iOS uses its own intrinsic height (~88pt of empty white for a field with nothing typed). `maxHeight` does not help, because the intrinsic height is already under any sane cap — this shipped and Trevor caught it as a composer that "got all huge". Fix: measure with `onContentSizeChange` and clamp (`INPUT_MIN_H`/`INPUT_MAX_H` in IntakeScreen), and short-circuit to the floor when the value is empty so it collapses after a send even if the callback doesn't fire on the way down.
- **JSX comments can't go in expression positions**: `{/* … */}` directly after `? (` or `return (` makes a second root element / invalid syntax. Use a plain `/* … */` there instead. This has broken HomeScreen and IntakeScreen once each — if tsc reports `TS1005 ')' expected` on a `<View style={{…}}>` line that looks fine, check for a JSX comment just above it.
- **tsconfig gotcha**: Expo's base config includes the DOM lib, so browser globals like `stop()`, `alert()`, `name`, `close()` typecheck fine and then crash at runtime in React Native. A dangling `stop()` call survived a refactor this way and silently broke the Player's close button. If a handler "does nothing," suspect a DOM global before suspecting the handler.
